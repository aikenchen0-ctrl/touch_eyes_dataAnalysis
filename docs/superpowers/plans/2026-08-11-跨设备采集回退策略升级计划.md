# 跨设备采集回退策略升级计划

## 1. 目标与边界

依据 `跨设备采集字段采集方式回退研究.md`，将 Android 原始采集升级为“能力可发现、来源可审计、退化可拒绝”的 schema v6 兼容扩展。原始 JSON 继续只读保留，当前训练模型的 `featureContract`、时间网格和默认模型不改变；本轮只改采集证据层和记录级质量元数据，不把新增姿态观察流直接送入模型。

`S0`：采集器能保存 IMU 与 `touchFrames[]` 数值，但传感器回退、触摸 MotionRange、单位/校准和运行中停流信息不完整；接触编码存在 `toolMajor/toolMinor` 静默代替触摸轴的风险。

`Sg`：每条原始记录都能回答“值来自哪个 Android 来源、单位和校准是否可信、该流是否健康、是否发生过退化、该触摸轴是否声明/观测/可能合成”，缺失时不伪造等价值；模型仍只消费既有固定合同。

## 2. 硬约束

1. 不按品牌或 ROM 写运行时分支；回退只依据实际传感器/输入能力和健康状态。
2. 原始数值不覆盖、不用零冒充缺失；派生线性加速度和姿态候选必须带独立 `sourceType`。
3. `GAME_ROTATION_VECTOR`、`ROTATION_VECTOR`、`GEOMAGNETIC_ROTATION_VECTOR` 分流保存，均 `trainingInput=false`。
4. 触摸按逐帧事件时间做 ZOH；`touchFrames[]` 不读取整次触摸结束后的聚合结果作为按下期输入。
5. 旧 schema v6 解析和现有模型资源保持兼容；新增字段为可选扩展。

## 3. 执行分支

### 分支 A：Android 采集能力与健康状态

- 传感器候选：线性加速度；否则普通加速度减同时间轴重力；无重力时记录为 `accelerometer_raw_no_gravity` 并标记 `trainingInput=false`，不伪装为线性加速度。
- 陀螺仪、重力和姿态观察流分别记录 `UNAVAILABLE/WAITING_FIRST_EVENT/HEALTHY/DEGRADED/STALLED`。
- 姿态优先 `GAME_ROTATION_VECTOR`，再独立回退到 `ROTATION_VECTOR`、`GEOMAGNETIC_ROTATION_VECTOR`；写入 `rotationFrames[]`，不进入现有模型矩阵。
- 记录 `streamEpoch`、来源、实际频率、时间戳回退/倒退计数和 API/设备构建信息。

验收：无对应传感器时记录明确 `UNAVAILABLE`；注册成功但无首帧时不是 `HEALTHY`；姿态候选不写入 `gameRotationFrames[]` 的错误来源；时间戳倒退不会无标记拼接。

### 分支 B：触摸轴来源与设备输入画像

- 保存 `InputDevice` 的 `MotionRange`：轴、来源、最小/最大/范围、flat、fuzz、resolution。
- 每个 `touchFrames[]` 保存 `pointerId/actionMasked/actionIndex`、事件/接收双时钟和逐轴 `declared/observed/synthesizedOrUnknown`。
- 保存 Android API、品牌/型号、构建指纹、显示尺寸/模式/旋转、View 尺寸、density/xdpi/ydpi、触摸坐标系和变换版本。
- 触摸轴缺失不补零为真实值；`toolMajor/toolMinor` 只作为独立观察字段，不覆盖 `touchMajor/touchMinor`。

验收：原始触摸字段和双时钟保存率 100%；每个 MotionRange 可追溯；缺失/未声明轴能与 0 值区分；触摸轴的 `source` 不再出现静默工具轴回退。

### 分支 C：跨层合同与自动校验

- 新增采集合同审计脚本，检查必需元数据、来源状态、双时钟因果字段、姿态流的 `trainingInput=false`、触摸轴质量和禁止回退。
- 更新 Android 单元测试与 `FunctionAndDataStructureDescription.md`，明确“新增字段是原始证据，不是模型通道”。
- 先不生成 `physical_mm` 训练特征；仅保存 `MotionRange`/DPI 候选，后续在真机矩阵通过后再生成 `physical_mm`、`view_covariance`、`shape_only` 三个派生合同。

验收：fixture 能通过正例；缺失来源、伪造姿态来源、工具轴覆盖、时间戳异常和 `trainingInput=true` 姿态流均能被拒绝；现有 Python 测试不回归。

## 4. 后续真机阶段

代码升级完成后，按 Pixel/AOSP、OnePlus/ColorOS、小米/HyperOS、vivo、华为/荣耀兼容层、三星以及 API `24–27/28–30/31–34/35+` 采集矩阵，覆盖刷新率、旋转、多窗口、后台、省电、游戏模式、低电量和热状态。只有在字段覆盖率、拒绝率、单设备 CV、跨设备误差和最差设备召回率达标后，才允许把派生合同接入训练消融。

## 5. 本轮交付物

- Android 原始采集兼容扩展（schema v6 可选字段）。
- 采集合同审计脚本与 fixture 测试。
- 本计划和 `FunctionAndDataStructureDescription.md` 更新。
- 不重新训练、不切换默认模型、不删除历史数据。

## 6. Android 正式构建合同

Android 构建必须在项目的 `android` 目录中，由 Windows Java 直接启动 Gradle Wrapper。标准调试 APK 的唯一正式构建命令为：

```powershell
java -classpath gradle\wrapper\gradle-wrapper.jar org.gradle.wrapper.GradleWrapperMain :app:assembleStandardDebug --no-daemon --max-workers=1
```

不得将 Bash、WSL 或 Unix 版 `android/gradlew` 作为正式构建路径。仓库内该脚本使用 CRLF 换行，Bash/WSL 可能把路径附带 `\r`，且 WSL 环境未配置 Java；这些失败不能作为 Android 源码或 Gradle 配置失败的判据。
